§1

Le sujet, en une page

IRC est un protocole de chat en texte brut sur TCP, né en 1988. Un serveur central écoute, des clients s'y connectent, s'authentifient, choisissent un pseudo, rejoignent des salons et s'envoient des messages. Chaque échange est une ligne de texte terminée par CRLF. Vous codez le serveur — jamais le client : à l'évaluation, un vrai client (irssi) se branche dessus.

Les contraintes 42 qui structurent tout le reste :

  • C++98 strict, compilé -Wall -Wextra -Werror.
  • Aucun fork, aucun thread. Un seul processus gère tous les clients.
  • Un seul poll() pour toutes les I/O — lire, écrire, accepter. Un recv ou un send non gardé par poll() est sanctionné à l'éval.
  • Tous les fd non-bloquants, via fcntl(fd, F_SETFL, O_NONBLOCK) et rien d'autre sur macOS.
  • Lancement : ./ircserv <port> <password>.

Cette dernière contrainte est le cœur du projet : elle interdit d'attendre un client. D'où toute l'architecture à buffers qui suit — on ne lit jamais un message complet d'un coup, et on n'écrit jamais directement.

§2

§3

Le trajet d'un message, de l'octet à la réponse

C'est la logique centrale du projet, et elle est déjà correcte dans votre code. Deux buffers par client font tout le travail : _inBuffer accumule les octets reçus jusqu'à trouver un CRLF, _outBuffer accumule les réponses jusqu'à ce que poll autorise l'écriture. Aucune I/O ne se fait hors de la boucle.

§4

La machine à états de l'enregistrement

Un client n'existe vraiment qu'une fois enregistré. Tant qu'il ne l'est pas, il ne peut rien faire d'autre que fournir ses trois informations. Votre implémentation appelle checkRegister() après chaque commande : dès que les trois conditions sont réunies, la bascule se fait et les quatre messages de bienvenue partent.

Dépassement de tampon sur une ligne de 512 octets

src/ServerClient.cpp:30–50

recv peut remplir les 512 cases du tampon, puis recvBuffer[bytesReceived] = '\0' écrit à l'indice 512 — une case après la fin. Le serveur meurt sur stack smashing. Or 512 octets est précisément la taille maximale d'un message IRC : ce n'est pas un cas tordu, c'est une entrée légale.

ReproductionSIGABRT · code de sortie 134

$ python3 -c "…envoie 'NICK ' + 'z'*505 + CRLF  → 512 octets"
  recv: b''                       ← le serveur a fermé
  >>> SERVER CRASHED — exit code 134 (abort)
- int bytesReceived = recv(fd, recvBuffer, sizeof(recvBuffer), 0); + int bytesReceived = recv(fd, recvBuffer, sizeof(recvBuffer) - 1, 0);

§9

Plan d'action pour finir le projet

Cinq lots, dans cet ordre. Les deux premiers sont séquentiels et non négociables : ils débloquent la compilation et posent les fondations que toutes les commandes suivantes vont réutiliser. Les lots 2 et 3 se parallélisent entre les deux binômes. Le lot 4 se fait à nouveau ensemble, juste avant de rendre.

La règle d'ordre à ne pas enfreindre

N'écrivez pas PRIVMSG avant le lot 1. Sans sendNumeric, chaque commande fabrique ses préfixes à la main — c'est exactement comme ça que PASS, NICK et PING se sont retrouvés avec un format non conforme pendant que JOIN avait le bon. À sept commandes restantes, ça fait une quarantaine de chaînes à réécrire une par une. Une heure investie maintenant en économise quatre plus tard.

Le patron de chaque commande

handleJoin a déjà établi la forme. Reprendre ces sept étapes dans cet ordre pour chaque nouvelle commande évite d'oublier une réponse d'erreur — c'est exactement ce que le correcteur teste.

  • 451 — le client est-il enregistré ?
  • 461 — a-t-on assez de paramètres ?
  • 401 / 403 — la cible existe-t-elle (utilisateur, salon) ?
  • 442 / 482 — l'émetteur est-il membre, et opérateur si l'action l'exige ?
  • Agir sur l'état — Channel ou Client.
  • Diffuser aux concernés, en n'oubliant pas l'émetteur quand il doit se voir agir.
  • Répondre à l'émetteur, puis tester à deux clients irssi avant de commit.

Checklist avant de rendre

  • make re passe sans un seul avertissement, deux fois de suite.
  • Aucun relink : un make immédiatement après un make ne fait rien.
  • Trois clients irssi connectés simultanément discutent dans le même salon.
  • Un client tué brutalement (kill -9) ne fait pas tomber le serveur ni les autres.
  • Une commande envoyée en deux morceaux avec une pause au milieu est traitée correctement.
  • Un message de 512 octets ne fait pas tomber le serveur.
  • Un mot de passe faux refuse la connexion.
  • Chaque mode — i, t, k, o, l — est démontrable en direct.
  • Un non-opérateur qui tente KICK reçoit bien 482.
  • Ctrl-C ferme tous les descripteurs, valgrind ne signale aucun bloc perdu.
  • Le README nomme le client de référence et la commande de lancement.

# compiler et lancer

# test brut : attention, netcat envoie \n seul, votre serveur exige \r\n
printf 'PASS pass\r\nNICK a\r\nUSER a 0 * :A\r\nJOIN #x\r\n' | nc -c 127.0.0.1 6667

# fragmentation : le message doit quand même être reconnu
printf 'PASS pa' ; sleep 1 ; printf 'ss\r\n'

# la ligne de 512 octets qui fait tomber le serveur aujourd'hui
python3 -c "import socket;s=socket.create_connection(('127.0.0.1',6667));s.sendall(b'NICK '+b'z'*505+b'\r\n')"

En résumé

Une vingtaine d'heures, soit une dizaine chacun — dont la moitié sur des commandes qui reprennent un patron déjà écrit. La partie réellement difficile (un poll unique, des fd non-bloquants, du buffering correct dans les deux sens) est derrière vous et fonctionne. Le vrai risque n'est pas technique : c'est que trois semaines viennent de passer pour deux commits de réorganisation. Faites le lot 0 aujourd'hui, le lot 1 cette semaine, et à partir du lot 2 le projet avance tout seul.
