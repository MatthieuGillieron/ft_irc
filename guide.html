Le projet en bref

Qu'est-ce que ft_irc, et quel est ton rôle dedans.

ft_irc = un serveur IRC écrit en C++98. Un programme qui écoute sur un port TCP, accepte plusieurs clients en même temps (irssi, WeeChat, netcat…) et parle le protocole IRC : authentification, pseudos, salons de discussion, messages privés, commandes d'opérateur.

La règle d'or du sujet : un seul processus, un seul poll(), des sockets non-bloquants. Pas de thread, pas de fork. Tout le monde est multiplexé dans une boucle unique.

La répartition dans l'équipe

Coéquipier 1Coéquipier 2 (toi)
Couche réseau & cycle de vie des connexions : boucle poll, buffering des données, parsing, signaux, robustesse (valgrind, déconnexions). Logique IRC & protocole : authentification, pseudos, channels, PRIVMSG, et les commandes opérateur (KICK/INVITE/TOPIC/MODE).

Les 3 fondations à blinder (dixit le sujet)

  1. La boucle poll() — surveiller tous les sockets d'un coup. fait
  2. Le buffering des données partielles — TCP peut couper un message en morceaux. fait
  3. PING / PONG — sans ça, les vrais clients coupent la connexion. fait
Bonne nouvelle : les 3 fondations sont déjà en place et testées. C'est le plus difficile du projet.

Le trajet d'un message

Quand un client tape NICK bob :

client tape "NICK bob\r\n"
↓ poll() détecte des données sur le socket
↓ recv() lit les octets → inBuffer du client
↓ on découpe sur "\r\n" → une ligne complète
↓ Message::parse() → { command:"NICK", param:["bob"] }
↓ dispatcher() aiguille vers handleNick()
↓ handleNick traite + écrit la réponse dans outBuffer
↓ poll() voit qu'il y a à écrire → flushClient() → send()
Point clé : on ne send() jamais directement dans un handler. On écrit dans le outBuffer, et c'est la boucle poll qui envoie quand le socket est prêt (via POLLOUT). C'est ça, le « buffer + POLLOUT » propre.

La boucle poll, en résumé

  1. Pour chaque client : écouter POLLIN (lecture), et POLLOUT uniquement s'il reste des choses à envoyer.
  2. poll() bloque jusqu'à ce qu'un socket ait quelque chose.
  3. Nouvelle connexion sur le socket d'écoute → acceptClient().
  4. Données sur un client → handleClient() (lire + découper + dispatcher).
  5. Socket prêt à écrire → flushClient().
  6. Déconnexions différées à la fin du tour (jamais au milieu).

Points clés à maîtriser

Ce qu'un examinateur va vraiment tester et te demander d'expliquer.

# Sockets non-bloquants

Chaque socket est passé en O_NONBLOCK via fcntl. Un recv/send ne bloque jamais le serveur : s'il n'y a rien, il rend la main immédiatement (EAGAIN). Indispensable pour servir N clients sans threads.

# Buffering des données partielles

TCP est un flux, pas des messages. "NIC" peut arriver, puis "K bob\r\n" plus tard ; ou deux commandes d'un coup. On accumule dans inBuffer et on ne traite une ligne que lorsqu'un \r\n complet est présent — dans une boucle, pour vider plusieurs commandes reçues ensemble.

# Enregistrement en 3 temps

PASS + NICK + USER doivent tous être fournis avant que le client soit registred. checkRegister() vérifie les 3 après chaque commande → l'ordre n'a pas d'importance. Une fois complet : messages de bienvenue 001 → 004.

# PING / PONG

Le client envoie régulièrement PING <token> ; le serveur doit répondre PONG <token>. Sans ça, irssi/WeeChat considèrent le serveur mort et coupent.

# Format des messages IRC

Réponses numérotées : :ircserv <code> <nick> <cible> :<message>. Le : final introduit un paramètre « trailing » qui peut contenir des espaces. Exemple : :ircserv 353 bob = #test :@bob alice.

# Gestion mémoire (zéro fuite)

Chaque new Client / new Channel a son delete (à la déconnexion et dans le destructeur du Server). Testé à la soutenance avec valgrind.

Dette technique à corriger : le format des erreurs n'est pas homogène. Les anciens handlers renvoient "464: Password incorrect" (format inventé) alors que JOIN utilise déjà le bon format :ircserv 403 …. À aligner avant la soutenance.

Rôle de chaque fichier

À quoi sert chaque fichier, ses fonctions clés, et pourquoi il est fait ainsi.

Vue d'ensemble : header/ = les déclarations (le « quoi »), src/ = le code (le « comment »). Les src/commands/ regroupent les handlers de commandes IRC (une famille par fichier), tous membres de la classe Server.

Point d'entrée

src/main.cpp

Le démarrage du programme : ./ircserv <port> <password>.

ÉtapeDétail
Argumentsexige exactement 3 arguments, sinon message d'usage
Portconverti puis validé dans la plage 1024–65535
SignauxSIGINT & SIGQUIT → g_shutdown=1 ; SIGPIPE → ignoré
Lancementcrée le Server et appelle run()

pourquoi SIGPIPE est ignoré : écrire dans un socket fermé par le client enverrait ce signal, dont le comportement par défaut tue le processus. g_shutdown est une variable globale sig_atomic_t car c'est le seul type qu'un handler de signal peut modifier sans risque.

Le cœur du serveur

header/Server.hpp & src/Server.cpp

La classe centrale : elle possède le socket, la boucle d'événements, tous les clients et tous les channels. C'est elle qui orchestre tout.

Membre / méthodeRôle
setupSocket()socket → SO_REUSEADDR → bind → listen → non-bloquant
run()la boucle poll : prépare les events, attend, traite lecture/écriture/déconnexions
acceptClient()accepte une connexion, la passe en non-bloquant, crée un new Client
handleClient(fd)lit avec recv, accumule dans le inBuffer, découpe par \r\n, dispatche
dispatcher()aiguille selon la commande (PASS, NICK, USER, PING, JOIN…)
flushClient(fd)envoie le outBuffer avec send, efface seulement ce qui est parti
disconnectClient(fd)ferme le fd, retire des pollfds + clients, delete
findClient(fd) / findChannel(name)retrouver un client (par fd) / un channel (par nom)

Les données membres

_listenFdle socket d'écoute
_pollfdsvector<pollfd> — tous les fd surveillés par poll
_clientsvector<Client*> — les clients connectés
_channelsmap<string, Channel*> — les salons, indexés par nom
_toDisconnectfd à fermer en fin de tour (jamais au milieu de la boucle)

pourquoi map pour les channels (recherche par nom, directe) mais vector pour les clients (on itère dessus à chaque tour). pourquoi _toDisconnect : supprimer un élément en plein milieu de la boucle décalerait les index et ferait sauter des clients — on diffère donc le nettoyage.

Les données

header/Client.hpp

Représente un client connecté. Classe « sac de données » : tout est inline dans le header (getters/setters simples), pas de .cpp associé.

AttributRôle
_fdle socket du client
_nickName / _userNameson identité
_passa-t-il donné le bon mot de passe ?
_registreda-t-il fini PASS + NICK + USER ?
_inBufferoctets reçus pas encore traités (données fragmentées)

pourquoi deux buffers : TCP est un flux, pas des messages. Le inBuffer absorbe les messages coupés en morceaux, le outBuffer permet d'envoyer « quand le socket est prêt » via POLLOUT.

header/Message.hpp & src/Message.cpp

Transforme une ligne brute en structure exploitable. Une seule fonction statique : Message::parse(line).

Message::parse("PRIVMSG #chan :hello world")
   → command = "PRIVMSG"
   → param   = [ "#chan", "hello world" ]

La structure Message ne contient que deux champs : command (string) et param (vector de strings).

pourquoi le : : dès qu'un paramètre commence par :, tout le reste (espaces compris) devient un seul paramètre « trailing ». C'est le mécanisme IRC pour transporter un message contenant des espaces.

Les salons

header/Channel.hpp & src/Channel.cpp

Représente un salon : ses membres, ses modos, son topic, ses règles. Ne touche jamais au réseau — c'est le Server qui l'utilise. Voir la section Dernières modifs pour le détail des méthodes.

pourquoi stocke des Client* (pointeurs) et non des copies : un client existe une seule fois en mémoire (dans le Server), le channel pointe simplement vers lui.

Utilitaires & build

header/Colors.hpp

Macros de couleurs ANSI (RED, GREEN, CYAN…) pour rendre les logs du serveur lisibles dans le terminal. Purement cosmétique.

Makefile

Compile le projet en C++98 strict (-Wall -Wextra -Werror -std=c++98). La variable SRCS liste les sources à la main : ajouter chaque nouveau .cpp ici. Règles utiles : make, make re (recompile tout), make fclean.

pourquoi les objets vont dans obj/ (via OBJDIR) pour ne pas polluer les sources.

Dernières modifs

La classe Channel et la commande JOIN, ajoutées récemment.

1 · La classe Channel

Fichiers : header/Channel.hpp + src/Channel.cpp. Un objet Channel représente un salon et répond à : qui est dedans, qui commande, quel est le sujet, quelles sont les règles.

CatégorieMéthodes
MembresaddMember, removeMember, isMember, getMembers, getMemberCount
Modos (opérateurs)addModo, removeModo, isModo
Invites (mode +i)addInvite, removeInvite, isInvited
Modes i/t/k/lsetInviteOnly, setTopicRestricted, setKey/removeKey, setLimit/removeLimit
Utilsbroadcast(msg, except), getNamesList()
Choix de conception : on a écrit dès maintenant tout ce dont les Phases 4 et 5 auront besoin (modes, invites), pour ne pas rouvrir ce fichier plus tard.

Deux détails qui évitent des bugs

  • removeMember appelle aussi removeModo → un membre qui part ne reste pas « modo fantôme ».
  • broadcast ajoute le \r\n et sait exclure l'expéditeur (paramètre except).

Note vocabulaire

Dans ton code on parle de modo (plus parlant), mais sur le réseau le protocole garde le terme « operator » : le préfixe @, le mode +o, l'erreur 482 restent inchangés.

2 · La commande JOIN

Fichier : src/commands/Join.cpp. C'est la première commande qui utilise la classe Channel. Découpée en 3 fonctions à responsabilité unique :

FonctionRôle
handleJoinOrchestration : valide, crée/trouve le salon, ajoute le membre, déclenche le reste
checkJoinVérifie les règles du salon : +i (473), +k (475), +l (471)
joinRepliesEnvoie topic (332) + liste des noms (353) + fin de liste (366)

Le déroulé de handleJoin

// 1. garde-fous
non enregistré        → 451
pas de nom de channel → 461
nom sans '#'          → 403

// 2. trouver ou créer le salon
chan = findChannel(name)  ou  new Channel(name)
déjà membre → return

// 3. règles (seulement si le salon existait déjà)
if (!created && !checkJoin(...))  → return

// 4. ajout + annonce

Testé et validé : deux clients rejoignant #test se voient mutuellement, le créateur apparaît en @bob (modo), et le broadcast d'arrivée fonctionne.

Questions / Réponses

Les questions typiques de soutenance — entraîne-toi à y répondre à voix haute.

Pourquoi un seul poll() et pas un thread par client ?
Le sujet l'impose, mais c'est aussi la bonne approche : poll() surveille tous les sockets d'un coup et nous dit lesquels sont prêts. Un seul processus, pas de synchronisation, pas de data race. On ne « perd » pas de temps à attendre car les sockets sont non-bloquants.
Que se passe-t-il si un message arrive en deux morceaux ?
On accumule tout dans le inBuffer du client. On ne traite une commande que quand un \r\n complet est présent. Un message coupé attend simplement le morceau suivant. À l'inverse, si plusieurs commandes arrivent ensemble, une boucle les traite toutes.
Pourquoi écrire dans un outBuffer au lieu de send() directement ?
Parce qu'un socket peut ne pas être prêt à écrire, ou n'accepter qu'une partie des octets. On stocke la réponse dans le outBuffer et on active POLLOUT ; la boucle poll envoie quand c'est possible, et flushClient n'efface que ce qui est réellement parti.
Pourquoi PING / PONG est-il obligatoire ?
Les vrais clients envoient des PING pour vérifier que le serveur est vivant. Sans réponse PONG, ils considèrent la connexion morte et se déconnectent au bout de quelques secondes.
Quelle différence entre PRIVMSG vers un user et vers un channel ?
Vers un user : message privé, un seul destinataire (on cherche le client par son nick). Vers un channel (#…) : broadcast à tous les membres du salon, sauf l'expéditeur. Les deux réutilisent findClient/findChannel + broadcast.
Qu'est-ce qu'un opérateur (modo) de channel ?
Un membre avec des droits d'administration sur le salon : il peut KICK, INVITE, changer le TOPIC (si +t), et modifier les MODE. Le créateur du salon en devient automatiquement un. Affiché avec un @ devant son pseudo. Un non-op qui tente une commande op reçoit l'erreur 482.
Pourquoi une map pour les channels et un vector pour les clients ?
On cherche toujours un channel par son nom → la map fait ça directement, sans boucle. Les clients, on itère surtout dessus (poll, broadcast) et on les cherche par fd → un vector suffit.
Comment éviter les fuites mémoire ?
Chaque new a son delete : à la déconnexion d'un client (disconnectClient) et pour tous les clients + channels dans le destructeur ~Server(). On vérifie avec valgrind qu'aucun bloc n'est perdu, y compris après Ctrl-C.
À quoi sert SO_REUSEADDR ?
Il permet de relancer le serveur immédiatement sur le même port sans attendre que l'OS libère l'ancien socket (état TIME_WAIT). Sans lui, on aurait « Address already in use » à chaque relance rapide.
Pourquoi ignorer SIGPIPE ?
Si on écrit dans un socket que le client vient de fermer, l'OS envoie SIGPIPE dont le comportement par défaut est de tuer le processus. On l'ignore (SIG_IGN) et on gère l'erreur d'écriture nous-mêmes.
